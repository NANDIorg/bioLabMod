# 10 — Техническая архитектура

Платформа: **NeoForge 1.21.x, Java 21**, Gradle (NeoGradle или ModDevGradle).

⚠️ Имена API ниже соответствуют NeoForge 1.21.x. Помеченные **[проверить]**
пункты обязательно сверить с актуальной версией перед реализацией — NeoForge
активно менял эти области.

### Самое важное архитектурное правило

**`biohazard-biology` не имеет зависимости от Minecraft.** Вся биологическая
математика — чистые функции над простыми типами. Следствия:

- Покрывается обычными JUnit-тестами, быстро, без игры
- Можно прогнать 100 000 итераций эволюции в тесте за секунды и проверить, что
  баланс сходится
- Невозможно случайно затащить в расчёт обращение к миру (главная причина лагов
  в подобных модах)
- Модель можно отлаживать и балансировать отдельно от игры

Это решение стоит того, чтобы его защищать на ревью. Весь дизайн из
[01](01-BIOLOGY-MODEL.md)/[01B](01B-GENOME-ENGINEERING.md) — это именно такая
математика.

## 2. Хранение данных

### Что где лежит — сводная таблица

| Данные | Где | Механизм | Почему так |
|--------|-----|----------|------------|
| Гены, симптомы, профили хостов, шасси, правила | Датапак | `DataPackRegistryEvent.NewRegistry` | Контент, расширяемый аддонами |
| **Штаммы мира** | Уровень | `SavedData` (`StrainManager`) | Создаются в игре, не контент |
| Состояние инфекции сущности | Сущность | `AttachmentType<InfectionState>` | Привязано к сущности, переживает сохранение |
| Иммунная память | Сущность | то же | |
| Хронические состояния | Сущность | то же, `copyOnDeath` для игрока | |
| **Загрязнение чанка** | Чанк + индекс уровня | `AttachmentType<ChunkContamination>` + `SavedData` индекс | O(1) доступ + нет сканирования мира |
| Индекс загрязнённых чанков, очереди | Уровень | `SavedData` (`ContaminationIndex`) | Чтобы никогда не итерировать по миру |
| Очаги эпидемий | Уровень | `SavedData` (`OutbreakRegistry`) | Абстрактная симуляция |
| Журнал изменений блоков (для откатa) | Чанк | аттачмент чанка, ограниченный размер | Обратимость порчи |
| Знание игрока (что открыл) | Игрок | `AttachmentType<KnowledgeState>` | Ядро дизайна. По конфигу — общее на мир |
| Очки и разблокировки исследований | Игрок или уровень | аттачмент / `SavedData` по конфигу | Сингл vs кооп |
| Карты протоколов, окна оптимума | Уровень | `SavedData` (генерируется от сида) | Одинаково для всех игроков мира |
| Штамм в предмете, титр, загрязнение предмета | Предмет | `DataComponentType` | Современный механизм 1.21 |
| Герметичность помещения | Block entity контроллера | NBT block entity + кэш в памяти | Привязано к блоку |

### Аттачмент сущности

```java
public static final Supplier<AttachmentType<InfectionState>> INFECTION =
    ATTACHMENT_TYPES.register("infection", () ->
        AttachmentType.builder(InfectionState::new)
            .serialize(InfectionState.CODEC)
            .copyOnDeath()          // хронические состояния переживают смерть
            .build());
```

### Что подтверждено по аттачментам NeoForge (сверено с офиц. документацией)

| Факт | Значение для нас |
|------|------------------|
| Аттачменты поддерживаются на **block entity, чанках и сущностях** | Наша схема хранения валидна |
| **Аттачменты уровня** появились в документации с **1.21.5+** | Если целевая версия ниже — `ContaminationIndex` и `StrainManager` только через `SavedData`. Это и так наш план |
| Для **ItemStack аттачменты вытеснены ванильными data components** | Подтверждает решение: образцы, картриджи, праймеры — через `DataComponentType`, а не аттачменты |
| Регистрация: `AttachmentType.builder(<поставщик значения по умолчанию>)` через `DeferredRegister` на mod bus | Как в примере выше |
| **Нет сериализатора → аттачмент не сохраняется.** `copyOnDeath` доступен только при наличии сериализатора | Для `InfectionState` и `KnowledgeState` сериализатор обязателен |
| `getData` на чанке/сущности **создаёт экземпляр по умолчанию**, если его нет | ⚠️ **Важно:** всегда проверять `hasData` перед чтением, иначе мы незаметно создадим состояние инфекции каждой сущности в мире и раздуем сейв |
| Синхронизация настраивается в билдере; `AttachmentSyncHandler` — в версиях **1.21.6+** (в 1.21.6–1.21.8 — через пример с `sendToPlayer`) | **Мы ей всё равно не пользуемся:** нам нужна выборочная, знание-ограниченная синхронизация своими пакетами (раздел 4). Автосинк отправил бы клиенту всё состояние, включая скрытое от игрока знание — это сломало бы ядро дизайна |

Последние две строки — самые важные. Проверка `hasData` перед `getData` должна
быть правилом код-ревью: это тихая утечка производительности и размера сейва,
которую легко не заметить.

**[проверить]** Точные имена API синхронизации различаются между 1.21.x — сверить
с документацией под конкретную целевую версию (ссылки в
[99-PRIOR-ART.md](99-PRIOR-ART.md)).

### Аттачмент чанка + индекс

```java
ChunkContamination {
    // максимум 4 штамма на чанк (конфиг). Слабейший вытесняется.
    Map<UUID, Entry> strains;
    record Entry(short concentration, long lastUpdateTick, BlockPos hotspot) {}
}
```

**[проверить] Критичный вопрос реализации:** можно ли прочитать/изменить
аттачмент **незагруженного** чанка? Растекание загрязнения должно работать и
там. Два варианта:

- **Вариант A (предпочтительный):** `ContaminationIndex` (SavedData уровня)
  хранит концентрации **как источник истины**, аттачмент чанка — только кэш для
  быстрого доступа загруженным чанком. Растекание работает целиком на
  `SavedData`, никогда не трогает чанки.
- **Вариант B:** работать только с загруженными чанками, а для выгруженных
  копить «отложенные изменения» в индексе и применять при загрузке.

**Решение: вариант A.** Он надёжнее, не зависит от деталей API загрузки чанков и
гарантирует, что растекание не вызывает загрузку чанков (это самая частая
причина катастрофических лагов в подобных модах). Аттачмент чанка остаётся для
совместимости и быстрого чтения, но синхронизируется из индекса.

## 3. Планировщик: как мод тикает

Единая точка входа, а не десять независимых тикающих систем. Это делает бюджет
производительности управляемым и измеримым.

```java
// Один обработчик на LevelTickEvent.Post
class BiohazardScheduler {
    void tick(ServerLevel level) {
        long t = level.getGameTime();

        // Сущности тикают сами, со сдвигом по entityId — равномерная нагрузка
        // (внутри EntityTickEvent: if ((entity.getId() + t) % 20 != 0) return;)

        if (t % 100 == 0)  contaminationSpread.step(level, BUDGET_CHUNKS);
        if (t % 100 == 50) corruption.step(level, BUDGET_BLOCKS);
        if (t % 40 == 0)   containment.revalidateFast(level);
        if (t % 1200 == 0) outbreaks.simulateNearby(level);
        if (t % 20 == 0)   machines.tickProcedures(level);
    }
}
```

### Бюджеты (конфигурируемые, со счётчиками в отладочном режиме)

| Система | Период | Бюджет |
|---------|--------|--------|
| Проверка инфекции сущности | 20 тиков, со сдвигом | — |
| Растекание загрязнения | 100 тиков | 64 чанка |
| Порча блоков | 100 тиков | 16 блоков на уровень |
| Быстрая валидация помещений | 40 тиков | только инварианты |
| Полный скан помещения | по событию блока | только при изменении внутри bbox |
| Симуляция близких очагов | 1200 тиков | все (чистая арифметика) |

**Обязательно:** команда `/biohazard debug perf`, показывающая фактическое время
каждой системы. Без неё невозможно держать анти-цель «не лагать».

## 4. Сеть и знание-ограниченная синхронизация

Это не только защита от читов — это **ядро игрового дизайна**. Клиент не должен
знать то, чего не знает игрок, иначе ломается вся система открытий из
[01B](01B-GENOME-ENGINEERING.md).

```java
// Регистрация (NeoForge 1.21)
@SubscribeEvent
static void onRegisterPayloads(RegisterPayloadHandlersEvent event) {
    var r = event.registrar("1");
    r.playToClient(StrainKnowledgeSync.TYPE, StrainKnowledgeSync.STREAM_CODEC, handler);
    ...
}
```

### Что отправляется клиенту

| Пакет | Когда | Содержимое |
|-------|-------|------------|
| `SelfInfectionSync` | При изменении | Полное состояние своей инфекции, доза, симптомы, стадии |
| `StrainKnowledgeSync` | При открытии | **Только открытые игроком** свойства штамма: имя, цвет, известные гены |
| `NearbySymptomsSync` | При изменении видимых | Компактный битсет видимых симптомов соседних сущностей (для рендера) |
| `LocalContaminationSync` | При смене чанка | Концентрация в 3×3 чанках для тумана и дозиметра |
| `ContainmentStatusSync` | Открыт GUI / изменение | Состояние помещения |
| `ResearchSync` | При изменении | Очки, разблокировки |
| `CodexSync` | При открытии | Открытые правила, родословная |
| `ProcedureResultSync` | По завершении | Выход, подсказки направления |

### Чего клиенту НЕ отправляется никогда

- Полный геном не изученного штамма
- Матрица конфликтов генов, которую игрок не открыл
- Окна оптимума протоколов
- Карта соседства рецепторов
- Раскладка промоторов не картированного шасси
- Истинный состав образца на экране дедукции

**Следствие для реализации:** экран дедукции считает варианты **на сервере** и
отправляет клиенту только список совместимых гипотез. Иначе любой мод-читер
вскроет механику.

## 5. Фреймворк многоблоков

Многоблоков много (пассажная камера, биореактор, шлюз, комплексы T4). Нужен
общий фреймворк, а не семь отдельных реализаций.

```
MultiblockPattern         — декларативное описание формы (слои символов + легенда)
MultiblockController      — block entity «мозга»
MultiblockValidator       — проверка формы, инкрементальная
MultiblockPart            — блок, знающий своего контроллера
```

Требования:
- **Инкрементальная валидация:** при изменении блока проверяется только
  затронутая часть, а не вся форма
- **Описание в датапаке** — чтобы аддоны могли добавлять свои формы, а модпаки
  менять размеры
- **3D-превью в Кодексе** из того же описания (по образцу Ponder из Create).
  ⚠️ Полезность этого подхода — оценка автора, не подтверждённая источниками.
  Фича дорогая: сначала прототип, потом решение
- Поддержка «мягких» форм: шлюз и герметичное помещение — не жёсткая форма, а
  условия (это отдельный механизм, см. раздел 6)

## 6. Сканер помещений (самая нетривиальная система)

```java
class RoomScanner {
    // Вызывается ТОЛЬКО при:
    //  - установке/разрушении блока внутри кэшированного bounding box помещения
    //    или на его границе
    //  - первичной активации контроллера
    //  - явном запросе игрока
    RoomScanResult scan(Level level, BlockPos controller) {
        // BFS по проходимым блокам, лимит объёма (конфиг, по умолчанию 4096)
        // Собираем: внутренний объём, граничные блоки, найденные компоненты,
        //           утечки (выход в неограниченное пространство)
    }
}
```

Оптимизации, без которых это будет лагать:

1. **Кэш bounding box** помещения. Событие блока вне bbox игнорируется за O(1)
2. **Жёсткий лимит объёма.** При превышении — ошибка, а не зависание
3. **Дебаунс:** несколько изменений блоков за один тик (взрыв, поршень) приводят
   к **одному** скану в конце тика
4. **Разделение проверок:** полный BFS только при изменении геометрии. Состояние
   фильтров/питания/дверей — быстрая проверка по списку известных компонентов
5. **Асинхронность не нужна и опасна** — при лимите 4096 BFS занимает доли
   миллисекунды. **[решение автора]** Не делать асинхронно: синхронизация с
   миром создаст больше проблем, чем решит

## 7. Энергия и совместимость

- **Только Forge Energy** (`IEnergyStorage`, capability `Capabilities.EnergyStorage`).
  Своей энергосистемы нет
- Регистрация через `RegisterCapabilitiesEvent`
- Жидкости — `IFluidHandler`, свои жидкости (питательная среда, растворитель,
  загрязнённая вода) с тегами
- Предметы/инвентари — `IItemHandler`
- Все материалы — через теги `c:` (см. [09-CONTENT-LIST.md](09-CONTENT-LIST.md))
- Fallback-рецепты через `neoforge:conditions` в датапаке: если техномодов нет,
  работают упрощённые рецепты из ванильных ресурсов

## 8. Клиентская часть

| Подсистема | Реализация |
|------------|------------|
| Слой заражения на сущностях | Один `InfectionRenderLayer`, регистрируется на **все** `LivingEntityRenderer` через `EntityRenderersEvent.AddLayers`. Работает с мобами чужих модов автоматически |
| Слои игрока | То же + отдельный слой для деформаций модели |
| Эмиссивные слои | Рендер-тип с полной яркостью |
| Постэффекты | Core shaders, **с мягкой деградацией** при отсутствии поддержки + отдельные тумблеры конфига |
| Туман и цвет | `ViewportEvent.RenderFog`, `ComputeFogColor` |
| Частицы среды | Свой `ParticleProvider`, частота от концентрации, строгий лимит частиц |
| Эмбиент и дозиметр | Клиентский звуковой цикл от концентрации |
| GUI машин | `AbstractContainerScreen` + свои виджеты |
| **Редактор генома** | Самый сложный UI. Отдельный экран с drag-n-drop по позициям цепи, дугами конфликтов, подсветкой промоторов |
| **Экран дедукции** | Список гипотез, приходит с сервера |
| Кодекс | Свой экран с навигацией, 3D-превью многоблоков, деревом родословной |
| HUD | Доза, состояние костюма, воздух, фильтр, симптомы, тревога |

**Предупреждение по производительности:** динамический свет от биолюминесценции
— потенциальная проблема. **[решение автора]** В v1 реализовать как **частицы +
эмиссивная текстура без реального освещения**, а настоящий динамический свет —
только опциональной интеграцией с модами динамического освещения. Свой
динамический свет вызовет перестройку чанков и просадки.

|---------|---------------|-----|
| **Юнит** | Весь `biohazard-biology`: геном, укладка, стабильность, фенотип, мутации, отбор, SIR, антигенная математика, дедукция | JUnit. **Это основная масса тестов** |
| **Свойства/фузз** | Codec round-trip для всех структур; невозможность собрать невалидный геном; монотонность формул | Генеративные тесты |
| **Симуляция** | 100 000 шагов эволюции: сходится ли баланс, вымирает ли летальный штамм, не улетает ли в бесконечность | Отдельные «балансные» тесты, прогон в CI |
| **GameTest** | Заражение, передача, порча, герметичность, утечки, деконтаминация, целостность костюма | NeoForge GameTest |
| **Производительность** | Бюджеты соблюдаются при 100 000 загрязнённых чанков и 500 заражённых сущностей | Бенчмарк-сценарий в CI |
| **API** | `biohazard-addon-example` собирается и работает | CI |

**Балансные тесты в CI — ключевая страховка.** Весь мод держится на том, что
эволюционная модель не улетает в крайности. Это надо проверять автоматически при
каждом изменении чисел.

## 11. Главные технические риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Загрязнение мира лагает | **Высокая** | Ленивый распад, индекс вместо сканирования, SavedData как источник истины, жёсткие бюджеты, бенчмарк в CI |
| Сканер помещений лагает при массовых изменениях блоков | Средняя | Кэш bbox, дебаунс, лимит объёма |
| Редактор генома получится непонятным | **Высокая** | Это UI-риск №1. Нужен ранний прототип UI и проверка на живых людях до написания остального |
| Эволюционная модель уходит в крайности | Средняя | Балансные тесты-симуляции, капы, `maxStrainsPerOutbreak` |
| Аттачменты чанков не читаются для выгруженных чанков | Средняя | Вариант A: SavedData как источник истины |
| Утечка скрытого знания клиенту | Средняя | Отдельный слой `KnowledgeTools`, расчёт дедукции на сервере, ревью каждого пакета |
| Слишком большой объём контента, не доделаем | **Высокая** | Строгий MVP, см. [15-ROADMAP.md](15-ROADMAP.md) |
| Рендер-слой падает на мобах чужих модов | Средняя | Защитные проверки, тесты с популярными модами |
| Несовместимость с Sodium/Embeddium по шейдерам | Средняя | Мягкая деградация, отказ от своего динамического света в v1 |
